# ADR-0005 — 架构降级为单模块三层（Superseded ADR-0002）

- 状态：Accepted
- 日期：2026-08-18
- 决策者：项目 Owner
- 关联：**Superseded ADR-0002**（DDD 分层架构与 Maven 多模块）

## 背景

审阅（REVIEW-001）发现 ADR-0002 的 DDD 6 模块方案与实际不符且过度：
1. 参考项目 Ciyo ciyo-asset 实为若依风格传统三层（controller/serviceImpl/mapper/entity），非 DDD，照 DDD 写无法对照参考代码。
2. comm_public_basic（鉴权复用对象）是传统三层，asset 走 DDD 与既有体系风格割裂。
3. 用户明确"前期不要过度发散设计，着眼于基础功能"——DDD 样板（聚合根/值对象/端口/ArchUnit）对基础 CRUD 是显著开销。
4. 团队栈（produce/new_mes）均为传统三层，DDD 学习成本拖慢基础功能落地。

## 决策

**降级为单 Maven 模块 + 传统三层 + 包按限界上下文分包**（chyinan 风格）。

### 工程结构

```
asset-backend/                              # 单 Maven 模块
└── src/main/java/com/sk/asset/
    ├── AssetApplication.java              # 启动类
    ├── config/                            # 配置（Spring Security、Swagger、Redis、AuthPort）
    ├── common/                            # 通用：异常、Result、常量、工具
    ├── auth/                              # 鉴权接入：AuthPort(HTTP 调 comm_public_basic)、TokenFilter、UserContext
    ├── controller/                        # 接口层：REST 控制器
    │   ├── asset/                         # 按限界上下文分包
    │   ├── category/
    │   ├── location/
    │   ├── lifecycle/
    │   ├── inventory/
    │   ├── depreciation/
    │   └── consumption/
    ├── service/                           # 业务层：Service + Impl（镜像 controller 包结构）
    │   ├── asset/
    │   ├── category/
    │   └── ...
    ├── mapper/                            # 数据访问层：MyBatis Plus Mapper（镜像包结构）
    │   ├── asset/
    │   └── ...
    ├── entity/                            # 数据实体（PO，对应表）
    │   ├── asset/
    │   └── ...
    ├── dto/                               # 请求/响应 DTO（按上下文分包）
    │   ├── asset/
    │   └── ...
    └── enums/                             # 枚举（按上下文分包）
        ├── asset/
        └── ...
```

### 分层依赖约束（取代 ADR-0002 的 DDD 依赖方向）

- `controller → service → mapper → entity`
- `controller` 不得直接调 `mapper`（禁止跨层）
- `service` 之间避免循环依赖；跨上下文 service 调用须显式注入，不得双向
- `entity`（PO）不外泄到 controller，必须经 `dto` 转换
- 跨上下文只通过 ID 引用（如 Asset 持有 userId，不持有 User 对象——User 数据来自 comm_public_basic）

### 持久层选型

- MyBatis Plus 3.5.x（与 comm_public_basic / produce 一致，团队熟悉）

## 备选方案

- **保留 DDD 6 模块（ADR-0002）**：未选。过度设计，与参考项目/既有体系不符，拖慢基础功能。
- **3 模块（web/core/common）**：未选。初期单模块足够，包按上下文分包已满足"分门别类"，后期需要再拆。
- **按资产类型拆多模块（it/fixed/equipment/consumable）**：未选。初期过度设计，跨模块共享内核复杂。

## 后果

- 正面：与 Ciyo/comm_public_basic/团队栈风格一致，基础功能最快落地；包按上下文分包满足"分门别类"；降低 AI/人接手认知成本。
- 负面：单模块后期体积膨胀时需拆分（届时走 ADR 决策）；跨上下文边界靠包名约定 + Code Review 兜底（无 ArchUnit 强制）。
- 约束：包按上下文分包的纪律由 Code Review 保证；跨层调用禁止由 Code Review + 可选 ArchUnit 单测保证。
- 后续：搭骨架时建好包结构骨架 + 可选的 ArchUnit 三层依赖校验测试。
- **ADR-0002 标记为 Superseded by 本 ADR**。
