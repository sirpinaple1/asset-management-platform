# M04 — 领用/借用单（ARE/BOR）审批流

## 职责

资产领用/借用申请的完整审批流：申请→审批（批准/拒绝）→资产状态联动。
对应现有系统 ARE 单，346 条历史数据。

> **2026-08-20 决策（前端原型对齐）**：原型将「领用&退库」「借用&归还」分为两个前端菜单。
> 借用不建独立模块，共用本单据流：`receive_receipt.type` 区分 RECEIVE-领用 / BORROW-借用，
> serial_no 前缀分别为 ARE / BOR，前端两菜单各自按 type 过滤同一接口。
> 资产状态机不变（借用中也算 IN_USE），`asset_allocation.type` 同步区分持有性质。

## 涉及的表

| 表 | 操作 |
|---|---|
| `receive_receipt` | 领用单主表（ARE单） |
| `receive_receipt_item` | 领用单明细（一单对多资产） |
| `asset` | 审批通过时 status: IDLE→IN_USE；拒绝时 status: PENDING_CONFIRM→IDLE |
| `asset_allocation` | 审批通过时新增持有记录 |
| `asset_log` | 领用/归还操作写入日志 |

## 状态机

```
（申请人提交）→ PENDING
PENDING → APPROVED  （审批通过：资产 IDLE/PENDING_CONFIRM → IN_USE）
PENDING → REJECTED  （拒绝：资产 PENDING_CONFIRM → IDLE）
```

## 对外 API

```
POST   /api/v1/receipts                  # 发起领用/借用申请（一次可申请多台资产，申请人取当前登录用户；locationId 必填）
GET    /api/v1/receipts                  # 列表，支持 status/date/userId/type 筛选（含明细行与资产名称，前端两菜单按 type 过滤）
GET    /api/v1/receipts/{id}             # 详情（含明细行）
POST   /api/v1/receipts/{id}/approve     # 批准（需有审批权限，审批人与申请人不能是同一人）
POST   /api/v1/receipts/{id}/reject      # 拒绝，body={reason}
```

> **姓名快照（2026-08-21 实施决策）**：ADR-0004 约定 asset 库不存用户主数据，
> 单据展示申请人/审批人/持有人姓名无法 JOIN 本库。V20260823 增加
> `receive_receipt.applicant_name`（提交时快照）、`approver_name`（审批时快照）、
> `asset_allocation.user_name`（发放时快照），对齐既有快照模式（department/operator_label）。

> **领用区域必填（2026-08-21 补充，用户验收反馈）**：领用后资产物理位置随人走，
> 若审批只写人/部门、不更新 location_id，盘点按位置扫资产会找不到实物。V20260827 给
> `receive_receipt` 加 `location_id`（存量单 NULL，审批时跳过位置更新兼容过渡）；
> 申请 DTO `@NotNull` 强制必填 + create 校验位置存在性（400）；
> **审批通过时资产 location_id 更新为领用区域**，日志追加"领用区域：XX"，
> 列表/详情回填 `locationName`。home_location_id（资产归属位置）不动，
> 归还/盘亏等场景仍可追溯资产"家"在哪。

## 业务约束

- 同一资产同时只能有一张 PENDING 状态的领用/借用单（提交时校验，领用与借用互斥占用）
- 审批人与申请人不能是同一人（或由权限体系控制，以 comm_public_basic 角色为准）
- 批准时对每台资产调 `AssetService.changeStatus(id, IN_USE, ...)`，事务内完成
- 领用单的 `serial_no` 格式：`ARE`（领用）/ `BOR`（借用）+ `yyyyMMdd` + 4位序号，当天按前缀分别自增

## 归还入口

归还操作不单独建单据（与现有系统保持一致），通过 `asset_allocation` 更新 `returned_at` 并调
`AssetService.changeStatus(id, IDLE, ...)` 实现（同一事务内：持有关系闭环 + 资产回闲置 +
资产持有人仍为本记录持有人时清空 user_id/user_department）：

```
GET  /api/v1/allocations                 # 持有关系列表（assetId/userId/type/active 筛选，含资产名称；前端"退库/归还"取 allocation id 的渠道）
POST /api/v1/allocations/{id}/return     # 归还，body={note}（可空），asset status: IN_USE → IDLE
```

## 完成标准

```
mvn clean verify 通过
POST /api/v1/receipts → code 200（统一 Result 契约，HTTP 状态码仅鉴权层使用），相关资产 status 变 PENDING_CONFIRM；缺 locationId → 400"领用区域不能为空"
POST /api/v1/receipts/{id}/approve → 资产 status 变 IN_USE + location_id 更新为领用区域，asset_allocation 有记录，asset_log 有记录（含领用区域）
POST /api/v1/receipts/{id}/reject → 资产 status 回 IDLE
同资产重复提交领用/借用申请 → 409（业务码，含占用单号）
审批人=申请人 → 403
```

## 实施记录（2026-08-21）

- 单号生成：`likeRight(前缀+日期) + orderByDesc + LIMIT 1 FOR UPDATE` 锁定读串行取号，
  `uk_receipt_serial_no` 唯一索引兜底
- `AssetService.changeStatus` 增加显式操作类型重载（M04 区分「领用/借用/归还」日志语义，
  原 4 参签名按目标状态推导、行为不变）
- 审批通过同时更新 `asset.user_id/user_department`（持有人随单据流转），拒绝不动持有人
- 归还时仅当资产当前持有人=本记录持人才清空（期间已转让则不动）
- 列表/详情均回填明细行（含资产编码/名称/序列号），前端列表"资产数"列直接取 items.length
