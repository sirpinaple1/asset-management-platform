# ADR-0003 — 多 Agent 上下文传承机制

- 状态：Accepted
- 日期：2026-08-18
- 决策者：项目 Owner

## 背景

项目将由多 Agent、多平台、多人经手。任何接手方拿到代码后，必须能在最短时间内建立精简但完整的上下文，延续进度而不破坏既有约定。需选定一套传承机制，避免上下文散落在 commit message、聊天记录、个人脑中。

## 决策

采用**分层文档传承机制**，四类文档各司其职：

| 文档 | 位置 | 职责 | 更新时机 |
|---|---|---|---|
| AGENTS.md | 根目录 | AI/人入口，精简索引 + 红线速查 + 接手约定 | 结构性变更时 |
| ENGINEERING.md | docs/ | 工程红线 + 设计原则主体 | 红线/原则变更时（须配 ADR） |
| STATUS.md | 根目录 | 当前进度、阶段、下一步、阻塞、待决策 | 每次阶段性进展后 |
| docs/adr/ | docs/adr/ | 架构决策记录（只追加，不改写） | 每个重大决策时 |

接手流程固化：`AGENTS.md → STATUS.md → ENGINEERING.md → 最近 ADR`。

## 备选方案

- 单文件 AGENTS.md（所有上下文浓缩一处）：简单，但文件会越长越臃肿，AI 读取成本高、人类浏览难。未选。
- `.ai/` 目录结构化：结构化强，但非通用约定，部分 AI 工具不默认读取 `AGENTS.md` 之外的路径。未选。
- 仅靠 commit message + 代码注释：上下文碎片化，无法承接跨会话决策。未选。

## 后果

- 正面：分层清晰，AI 按"入口→进度→规范→决策"顺序建立上下文；STATUS.md 保证进度可视；ADR 保证决策可追溯。
- 负面：需维护多份文档，有纪律成本（已写入红线 R7：进展必须更新 STATUS，决策必须写 ADR）。
- 约束：AGENTS.md 保持精简（不超长），细节一律指向 ENGINEERING.md / ADR；ADR 不可篡改历史，只能新增 Superseded。
- 后续：每次 Agent 会话开始前强制读 AGENTS.md；红线 R7 由 Code Review 兜底。
